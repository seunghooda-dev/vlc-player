# 분석: blackframe→blackdetect 필터 전환 — no-go 결정

- 작성일: 2026-07-15
- 결론: **전환하지 않는다.** 현행 blackframe+구간 스티칭 유지.
- 배경: 감사 노트에 "blackdetect로 바꾸면 수동 스티칭 로직이 없어진다(순수 단순화)"가
  후보로 있었고, 전제 조건은 "동작 동일 검증"이었다. 구현 전 정밀 분석에서 이 전제가
  성립 불가함을 확인했다.

## 1. 픽셀 임계값 의미 불일치 (결정적)

| | blackframe (현행) | blackdetect (후보) |
|---|---|---|
| 파라미터 | `threshold` 0–255 (기본 32) | `pix_th` 0.0–1.0 (기본 0.10) |
| 의미 | **원시 픽셀값** Y < threshold | **레인지 정규화**: 절대임계 = 휘도최소 + pix_th × 레인지크기 |
| limited range(16–235) 등가 | threshold=32 | pix_th = (32−16)/219 ≈ **0.073** |
| full range(0–255) 등가 | threshold=32 | pix_th = 32/255 ≈ **0.125** |

방송 MXF는 대부분 limited range지만 혼재하며, ffprobe `color_range`가 `unknown`인
소재가 흔하다. 파일별 등가 pix_th를 신뢰성 있게 결정할 수 없음 → 같은 설정으로
**검출 결과 자체가 달라질 수 있다**(블랙 미검출/과검출 — QC 도구 최악의 회귀).

## 2. 부차 불일치

- **end/tc_end**: 현행 end = 마지막 블랙 프레임의 시각(프레임 인덱스 기반 TC).
  blackdetect `black_end` = 블랙이 끝난 시각(다음 프레임) → tc_end가 1프레임 밀림.
- **frames**: 현행은 실제 매칭 프레임 수(단일 프레임 구간은 UI에서 노란색 강조).
  blackdetect는 시간만 제공 → 역산 근사(반올림 오차).
- **UI 결박**: RightPanel의 amount(%)/threshold(0–255) 스핀박스와 저장된 사용자
  설정이 blackframe 의미에 결박 — 필터 교체 시 기존 설정이 조용히 재해석된다.
- **d(min duration)**: blackdetect 기본 2.0s. 단일 프레임 검출을 위해 d≈1/fps로
  내려야 하며 fps별 경계 동작 검증이 추가로 필요.

## 3. 판단

- 현행 구현은 정확함이 실측으로 확정돼 있다(2026-07-14 L-3 분석: blackframe 출력
  프레임 완전 연속, 스티칭 로직 결함 없음).
- 얻는 것은 ~40줄 단순화, 거는 것은 핵심 QC 판정의 의미 변화 가능성.
  로컬 샘플 A/B(2~3개)로는 레인지×비트심도×코덱 행렬을 증명할 수 없다.
- "고장나지 않은 것을 리팩터링하지 않는다" — no-go.

재고 조건: 전 소재가 레인지 메타데이터를 신뢰성 있게 제공하거나, blackdetect가
원시 임계 모드를 지원하게 되는 경우.
